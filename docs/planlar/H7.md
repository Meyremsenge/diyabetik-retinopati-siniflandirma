# H7 (30 Kasım – 6 Aralık) — Sunum ve teslim

> Teslim haftası. Yeni deney, yeni özellik veya model değişikliği **yok**.
> İndeks: [PLAN.md](../PLAN.md) · Biçim: [H1.md](H1.md) · Kaptan: **tüm ekip**

## Haftanın akışı (kim kimi bekler)

```text
Herkes: 7.1 (slaytlar, hafta başı) → 7.2 (demo senaryosu + 2 prova) → 7.3 (rapor teslimi)
M: 7.4 (repo son kontrol + v1.0 etiketi) ← 7.3 öncesi son PR'lar birleşmiş olmalı
```

## Bu haftaya özel ortak notlar

- Slayt ve rapordaki her sayı DENEY_KAYDI'ndan; slaytta da "tıbbi teşhis yerine geçmez" ifadesi bulunur.
- Slayta APTOS/IDRiD görüntüsü koymadan önce veri setinin kullanım koşullarını kontrol edin (doğrulanmadı); konursa kaynak slaytta yazılır. Slayt dosyası (`.pptx`/`.pdf`) **git'e girmez** → ekip içi Google Drive.
- Demo **internetsiz** çalışmalı: checkpoint yerelde, `pretrained=False` yükleme (4.5), venv hazır.

## 7.1 — Sunum slaytları

`[E]` · Dal: — (slaytlar git dışı; yalnız PLAN güncellemesi `<isim>/7.1-sunum`) · Öncelik: Must

**Hazır prompt:** `/durum 7.1` → kendi slaytlarını hazırla → `/bitir`

**1. Amaç:** Herkesin kendi sorumluluk alanını anlattığı, ~15 dakikalık tek bir sunum hazırlamak.

**2. Önkoşul:** 5.5 (rapor bölümleri), 5.1 galeri, 5.2 süre ölçümü.

**3. Dosyalar:** Drive'da `VisionDx_sunum` (git dışı). Değiştir: `docs/PLAN.md`.

**4. Arayüz — slayt akışı ve sahipleri (EKIP_REHBERI §1):**
| Sıra | Konu | Sahip | Kaynak |
|---|---|---|---|
| 1 | Problem, amaç, kapsam (1–2 slayt) | Ekip (açılışı yapan) | RAPOR §1–§2 |
| 2 | Veri seti, tekrar görüntüler, bölme, ön işleme | Rümeysa | RAPOR §4, §5.1, §5.3 |
| 3 | Model, transfer learning, eğitim düzeni | Büşra | RAPOR §5.2, §6 |
| 4 | Metrikler, sonuçlar (val/test/IDRiD), hata analizi, Grad-CAM | Meyrem | RAPOR §7–§9 |
| 5 | Canlı demo (7.2) | Meyrem | RAPOR §10 |
| 6 | Sınırlılıklar, etik, gelecek çalışma | Ekip | RAPOR §11–§12 |

**5. Adımlar:**
1. Ortak şablon tek kişi tarafından açılır; herkes kendi slaytlarını ekler.
2. Her slayt en çok 1 tablo veya 1 görsel; sayılar DENEY_KAYDI'ndan kopyalanır.
3. Her kişi kendi bölümü için 3 olası soru + cevap hazırlar (ör. "Neden accuracy değil QWK?", "Test'i neden bir kez kullandınız?", "Grad-CAM lezyon mu gösteriyor?").

**6. Test / doğrulama:** Bir kişi tüm slaytlardaki sayıları DENEY_KAYDI ile karşılaştırır.

**7. Kabul ölçütü:**
- [ ] Slaytlar Drive'da tam; her kişinin bölümü ve soru-cevap notu hazır.
- [ ] Sayılar DENEY_KAYDI ile birebir; "tıbbi teşhis yerine geçmez" ifadesi var.

**8. Sık hatalar:** Val sonucunu test sonucu gibi sunmak → her tabloda hangi küme olduğu yazar.

**9. Ekibe açıklama:** Jüri her kişiye kendi bölümünden soru sorabilir; herkes kendi kodunu `/anlat` notlarıyla tekrar etmeli.

**10. Tahmini süre:** Kişi başı 3–4 saat.

## 7.2 — Demo senaryosu + 2 prova (internetsiz)

`[E]` · Dal: `meyrem/7.2-demo-senaryo` · Öncelik: Must

**Hazır prompt:** `/durum 7.2` → `/bitir`

**1. Amaç:** Demonun sunumda internetsiz ve aksamadan çalışmasını iki provayla garanti etmek.

**2. Önkoşul:** 5.2 (demo son hâli), 7.1 taslağı.

**3. Dosyalar:** Değiştir: `README.md` ("Demo senaryosu" kısa bölümü), `docs/PLAN.md`. Örnek görüntüler git dışı (`outputs/demo_samples/`).

**4. Arayüz — senaryo (≈ 3 dk):**
1. Uygulama zaten açık (model önbellekte; ilk yükleme yavaşlığı sunumda yaşanmaz).
2. Uyarıyı göster ("akademik prototip, tıbbi teşhis değil").
3. **Val**'den 3 görüntü: doğru tahmin edilmiş bir DR yok, doğru tahmin edilmiş bir ağır/proliferatif, **yanlış** tahmin edilmiş bir örnek (dürüstlük; Grad-CAM yorumu).
4. Geçersiz dosya → hata mesajı.
5. Süreyi göster (`Süre: x.x sn`).

**5. Adımlar:**
1. 3 örneği 5.1 galerisinden seç → `outputs/demo_samples/`'a kopyala (sunum bilgisayarında).
2. **Prova 1:** Wi-Fi kapalı, sunum bilgisayarında: venv aktif → `streamlit run app/streamlit_app.py` → senaryo. Süre ve aksaklık not edilir.
3. Aksaklıkları düzelt (yalnız ortam/README; uygulama kodu değişirse 5.2 kartının testleri tekrar koşar).
4. **Prova 2:** Tam sunum akışı içinde, yine internetsiz. Yedek: demo ekran kaydı (video) Drive'da.

**6. Test / doğrulama:** İki prova da internetsiz başarıyla tamamlandı.

**7. Kabul ölçütü:**
- [ ] Prova 1 ve 2 internetsiz, hatasız; tarih ve süre PR açıklamasında.
- [ ] Yedek ekran kaydı Drive'da; README'de senaryo bölümü var.

**8. Sık hatalar:**
| Belirti | Çözüm |
|---|---|
| İnternetsiz açılışta model indirme hatası | Bir yerde `pretrained=True` kalmış; demo `best.pt` içindeki config ile `pretrained=False` yükler (4.5) |
| Streamlit tarayıcıyı açmıyor | Adresi elle aç: `http://localhost:8501` |
| Sunum bilgisayarında venv yok | Prova 1 tam da bunu yakalamak için; kurulum sunum gününden önce |

**9. Ekibe açıklama:** Yanlış tahmin örneğini göstermek kasıtlıdır: sınırlılıkları açıkça göstermek, akademik dürüstlüğün parçasıdır.

**10. Tahmini süre:** 2 prova × 30 dk + hazırlık 1 saat.

## 7.3 — Final rapor teslimi

`[E]` · Dal: `<isim>/7.3-rapor-teslim` · Öncelik: Must

**Hazır prompt:** `/durum 7.3` → `/bitir`

**1. Amaç:** Raporu dersin istediği biçimde (PDF vb.) teslim etmek.

**2. Önkoşul:** 6.5 (cila), 7.4 öncesi son sayılar.

**3. Dosyalar:** Değiştir: `docs/RAPOR_TASLAGI.md` (son hâl), `docs/PLAN.md`. PDF git dışı (Drive + teslim sistemi).

**4. Arayüz:** Teslim biçimi dersin yönergesinden alınır; **varsayılmaz**.

**5. Adımlar:**
1. Ders yönergesini (sayfa sınırı, kapak, biçim) kontrol et.
2. Markdown → PDF (ör. VS Code "Markdown PDF" eklentisi veya Word'e aktarım); tablo ve görsellerin bozulmadığını kontrol et.
3. Kapakta öğrenci numaraları gerekiyorsa yalnız PDF'te yazılır; **repodaki dosyalara eklenmez**.
4. Teslim + teslim onayının ekran görüntüsü Drive'a.

**6. Test / doğrulama:** PDF'i baştan sona bir kişi okur; tüm tablolar ve görseller görünür.

**7. Kabul ölçütü:**
- [ ] Rapor süresinde teslim edildi; onay Drive'da.
- [ ] Repoda öğrenci numarası yok (`git grep -nE "[0-9]{9,}" -- docs` sonuçlarını gözle kontrol et).

**8. Sık hatalar:** PDF'te Türkçe karakter bozuk → UTF-8 ile dışa aktar veya Word üzerinden PDF al.

**9. Ekibe açıklama:** Teslim edilen PDF ile repodaki rapor aynı sayıları içermeli.

**10. Tahmini süre:** 2 saat.

## 7.4 — Repo son kontrol + `v1.0` etiketi

`[M]` · Dal: `meyrem/7.4-repo-son-kontrol` · Öncelik: Must

**Hazır prompt:** `/durum 7.4` → `/bitir`

**1. Amaç:** Repoyu teslim edilebilir hâle getirmek ve `v1.0` etiketiyle dondurmak.

**2. Önkoşul:** 7.2 ve 7.3'ten gelen son PR'lar `main`'de.

**3. Dosyalar:** Değiştir: `README.md`, `docs/PLAN.md`; gerekirse `.gitignore`. Silme yalnız kullanıcı onayıyla.

**4. Arayüz:** —

**5. Adımlar:**
1. `git switch main && git pull`; `python -m pytest -q` → yeşil.
2. Gizlilik taraması (her biri boş olmalı):
   ```powershell
   git ls-files | Select-String -Pattern '\.pt$|kaggle\.json|\.env$|gptilekonuşma|^data/|^outputs/'
   git ls-files | Select-String -Pattern '\.(png|jpe?g)$'
   ```
   İkinci listede yalnız `docs/figures/` altındaki grafikler (CM, eğitim eğrisi) olabilir; veri görüntüsü olmamalı.
3. README kontrolü: kurulum (Windows + macOS), veri indirme, eğitim, tahmin, değerlendirme, demo, checkpoint konumu, uyarı. CLAUDE.md komut tablosu ile aynı mı?
4. Gereksiz dosya listesi (boş iskelet, kullanılmayan config, `HANDOFF.md` vb.) → kullanıcıya göster, **onayla** sil.
5. PLAN.md: tüm maddelerin son durumu doğru; "Plan dışı eklenen maddeler" güncel.
6. Bu dal PR ile `main`'e girdikten sonra: `git tag -a v1.0 -m "VisionDx v1.0 — teslim"` (main üzerinde). `git push origin v1.0` **yalnız kullanıcı onayıyla**.

**6. Test / doğrulama:** `python -m pytest -q` yeşil; adım 2 taramaları temiz; `git tag -l v1.0` etiketi gösteriyor.

**7. Kabul ölçütü:**
- [ ] Testler yeşil; repoda veri, checkpoint, anahtar ve öğrenci numarası yok.
- [ ] README ve CLAUDE.md komutları güncel ve tutarlı.
- [ ] `v1.0` etiketi `main`'de (push kullanıcı onayıyla).

**8. Sık hatalar:**
| Belirti | Çözüm |
|---|---|
| Etiket yanlış commit'e atıldı | Push edilmediyse `git tag -d v1.0` ve doğru commit'te tekrar; push edildiyse kullanıcıya sor |
| `.pt` dosyası geçmişte commit'lenmiş | Bu dosyadan kaldırmak yetmez (geçmişte kalır); dur ve ekiple konuş |

**9. Ekibe açıklama:** `v1.0` etiketi teslim anındaki kodu sabitler; jüri veya hoca tam o sürümü inceleyebilir.

**10. Tahmini süre:** 1,5–2 saat.
